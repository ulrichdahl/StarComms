01 Scope

In

  • Multi-guild service, one hosted fleet, licensed per guild from an owner-only admin surface.
  • Two session structures: command & squads, joint operations.
  • Four spoken verbs: alert, broadcast, hail, command.
  • Raw-audio relay. Optional attenuation or hard mute of others during relay, per guild.
  • Text mirror per transmission, ack button, ack reflected as reaction on source net.
  • /star-bridge self-service setup, auto teardown, transferable fleet lead.
  • Squad leads: commander-assigned, one per net, announced by voice. The lead is the squad's only reply channel (§8).
  • Button-gated voice replies, squad → command. No speech detection on squad nets (§5).
  • SQLite on host-mounted volume. Compose for dev and prod.
  • en + da trigger detection.

Out

  • Audio recording or archival. Transcripts persist; audio never touches disk.
  • TTS in the relay path — the relay copies audio. TTS is used only for spoken announcements (§5).
  • Billing. Cross-guild relay within one session.
Blocking acceptance criterion

Listener posts a relay-and-transcription notice in the command net chat on join, listing reachable channels. No audio persistence. GDPR + Discord ToS.

Squad nets are selfDeaf and receive nothing except while their lead has an open reply, where only the lead's stream is subscribed and nothing is transcribed. The squad net notice must say exactly this — “deaf unless your lead is replying” is a stronger and more honest claim than “we discard what we hear”, and the design earns it.

02 Fleet & slots

One voice connection per bot user per guild — hard Discord limit, open and unanswered since Oct 2022. Fleet = N applications, N tokens, one process.

The limit is per guild

One token holds one connection in every guild concurrently. N=12 serves 12 nets per guild, not 12 total. Fleet size caps nets-per-guild; guild count is unbounded.

QuantityValueNote
Fleet size N12Alfa–Lima

Per-guild quota≤ NAdmin policy value; what the wizard offers
Guilds servedunboundedUntil 2,500-guild shard threshold

Member k is named for callsign k (Star Bridge Alfa…) and always occupies that callsign's channel — member list doubles as the net map. Member Alfa is controller: sole slash-command registrant, sole holder of channel-management permissions.

Wizard offers only currently-free slots and names the holder when exhausted.

Provisioning is manual

No API creates Discord applications. N members = N hand-registered apps + N privileged GUILD_MEMBERS toggles. Tokens are shown once. Build against N=3.

Flat per guild, allocated in order across all concurrent sessions. Command nets take letters first. Required for hail to resolve to exactly one channel regardless of which session owns it.

04 Channel provisioning

Rate limit that kills the naive design

Channel name/topic PATCH is limited to ~2 per 10 min per channel — long undocumented, repeatedly reported. Never rename a channel to repurpose it. Create/delete churn per session also burns route buckets for nothing.

Hidden pool. On licensing: create category STAR BRIDGE + N voice channels named per callsign + 1 text channel. Created once, named once, never renamed. Sessions reveal/hide via @everyone overwrites on VIEW_CHANNEL + CONNECT. User-visible behaviour is identical to create/delete.

EventActionCost
Guild licensedCreate category + N voice + 1 text, all deniedonce/guild
Session startAllow overwrites on session nets; fleet joins1 PATCH/net
Session endMove stragglers out, deny overwrites, fleet leaves1 PATCH/net
Guild unlicensedDelete category + channelsonce/guild

Side effects: fleet may stay parked across sessions in a busy guild (join chime is client-side, unsuppressable — only remedy is not rejoining); a crash leaks a stale overwrite, not an orphaned channel. Boot sweep repairs.

05 Call-up protocol

A transmission is two utterances, not one. Call-up (verb + callsign) opens the net; the bot confirms with Ready to the caller and Attention to the targets; the message then relays live. Routing is resolved before the message exists.

Alertno callsign → all session nets. Preempts an open net. Target cue = Horn.
Broadcastno callsign → all session nets. Respects busy nets, skips them.
Hail<callsign> → another command/ops net, guild-wide.
Command<callsign> → one squad net in session.

State machine, per source net

IDLE→ call-up recognised, lock acquired→ OPENING→ cues played, Dc→ OPEN→ silence / out / max hold→ CLOSING→ IDLE

Why the cues must be duration-matched

Ready and Attention/Horn start on the same instant and are normalised to the same length Dc, so the caller's go-ahead and the receivers' alert end together. The first word of the message therefore cannot land while a receiver is still hearing a cue. Startup validates that every cue asset in a set matches Dc and fails loudly if not — a mismatch silently clips first words.

Cue sets are per guild: shipped defaults (en, da) or operator-supplied WAVs. All assets pre-encoded to Opus frames and cached in memory at startup — no ffmpeg spawn per cue, constant playback latency. Prepend ~200 ms silence pre-roll to every asset (§6).

Announcements

Distinct from cues, and the reason TTS is in the runtime at all. One exists in v1: squad lead promotion (§8).

CueAnnouncement
Contentfixed phrasecarries a member name
Lengthnormalised to Dcvariable — nothing races it, so no equal-duration constraint
Generationpre-encoded at startupTTS on promotion, cached in memory per (locale, spoken name)
Timingnet open / closequeued behind an open net
Announcements cannot be localised per listener

A bot transmits one stream into a channel; Discord has no per-member audio. The announcement is rendered once, in the session locale, and everyone in the net hears that language. The accompanying text line is one message, so the same applies. Per-listener language is not achievable and must not be promised.

  • Never played over an open net. If the target is OPEN, queue until CLOSING. If the wait exceeds max_hold_ms, drop the audio and keep the text line — a promotion announcement landing on top of an order is worse than a silent promotion.
  • TTS sits behind a driver interface, same shape as STT: piper_local default, fake for CI.
  • Names are arbitrary user strings. Resolution order: per-guild spoken_names override → sanitised display name (strip emoji, zero-width, out-of-locale scripts, collapse whitespace) → if nothing speakable remains, play the fixed lead_assigned cue with no name. The text line always shows the real display name.
  • Synthesised audio is cached in memory, never written to disk — the no-audio-on-disk rule (§1) stays absolute.

Immediate close on the terminator verb: out / slut.

Collision

One lock per target net. hail / command / broadcast against a held net → Busy cue to the caller, target untouched; for broadcast the held nets are skipped and named in the mirror embed. alert preempts: the holding relay is closed with Out and the alert takes the net. Mixing two callers into one net is never done.

Reply path, squad → command

A squad's lead can answer the commander by voice. The reply is button-gated, never speech-detected: the lead presses Reply on the order embed, and the reverse net opens without any recognition step.

Receiving is not detecting

This is what keeps question 7 from being expensive. The bot already knows who is replying and where the reply goes, so there is no call-up to recognise and no STT on squad nets at all. Recognition cost stays proportional to command nets, not to total nets. A button is also a better push-to-talk than a spoken call-up when the lead is already under fire.

tSquad netCommand net
0lead presses Reply—
openundeafen, cue Ready (Dc)cue Attention (Dc). Ducking engages
open+Dclead speaks — squadmates hear them natively, in the roomlive relay of the lead's stream only
closecue Out, re-deafencue Out. Ducking releases
  • Only the lead's SSRC is subscribed. Everyone else in the squad net is discarded unread, so a reply carries one voice rather than the whole room.
  • Target is unambiguous — the net that sent the order — so a reply needs no verb and no callsign.
  • Same lock, cues, and timers as a forward transmission. Commander already transmitting → Busy cue to the lead; no queueing, since the lead can hear that the net is in use.
  • No new cue assets. Ready, Attention and Out are reused with source and target swapped.
  • A text reply is offered alongside, for a lead who cannot speak. It posts into command/ops tagged with the squad callsign and is stored as a reply with no audio.

Detection

Opus RTP /SSRC→ decode→ 48k st → 16k mono→ VAD (silero)→ STT on call-up utterance→ parse verb + callsign→ lock + open

Per-SSRC, SSRC→user_id mapped, so every transmission is attributed. Detection runs only in state IDLE; while a net is OPEN the source audio is relayed, not parsed.

Fleet SSRC suppression — highest-consequence bug available

Joint ops: every net has a listener, so cues and relayed audio land in listening channels. Unguarded, an Attention cue or a relayed call-up re-triggers detection. Drop all audio from fleet user IDs before detection, unconditionally, both modes. Assert in unit tests.

Trigger authority: fleet lead + optional configured role. Others are audible locally, cannot open a net.

Callsign matching

  1. Normalised exact match on active callsigns.
  2. Normalised Levenshtein, tight threshold, restricted to callsigns currently allocated in this guild (≤12 candidates).
  3. alias_variants lookup — per-guild learned misrecognitions.

No match → Negative cue in the source net, no lock taken, plus an ephemeral heard “charly” with one click to record as a variant. The caller gets audible confirmation of failure rather than talking into a void. Never guess a route.

Double-metaphone is deliberately excluded — English-orthography-tuned, poor fit for Danish STT output. Layers 2–3 are phonetics-free.

06 Relay path

Once a net is OPEN, source PCM is copied to the target stream as it arrives. No buffering, no catch-up, no partial-transcript race — the route was resolved before the message was spoken.

Latency

StageBudgetNote
VAD segment end (call-up)~100 mssilero
STT on a ~1 s call-up200–600 msLocal GPU, small model, hotword-biased
Lock + open streams<50 msIn-process, fleet parked
Cue playback Dc1200 msHides mute latency and stream ramp-up
Message relayreal timeNo added delay for the whole transmission
Consequence: streaming STT is no longer required

The recognition window is one short fixed utterance, and its latency sits in dead air before the cue where nobody is transmitting. Chunked local Whisper now delivers the same feel as a streaming cloud recogniser, so local is the default and cloud is an option, not the price of real-time. STT volume also drops from continuous transcription to one ~1 s clip per transmission.

Stream continuity

  • Once OPEN, the target stream stays up and emits silence frames between utterances. Restarting a stream per utterance clips first words.
  • ~200 ms silence pre-roll on every cue asset, for the same reason on net open.
  • @discordjs/voice already emits the trailing silence-frame sequence — leave it alone, it prevents last-packet repeat on receivers.

The call-up itself is consumed, not relayed. Targets hear the cue, not “Command Charlie”. The addressed callsign appears in the mirror embed (§7).

Ducking the receiving net

Engaged at net open, released at close — once per transmission, not per utterance, and inside the Dc cue window where its latency is invisible.

Priority speaker (default)Hard mute (opt-in)
MechanismPRIORITY_SPEAKER on relay bots; clients attenuate others while bot transmitsPATCH member mute:true at open, restore at close
Cost0 API calls2 req/member/transmission
Latencyinstant~1 s, hidden inside the cue window
Determinismbest-effort — attenuation is a client-side settingabsolute
Failure modelistener hears bothcrash leaves humans muted

Hard mute guards: member-count ceiling → degrade to attenuation; bounded concurrent request pool; pre-mute state written to mute_state before first request so boot sweep restores. The per-transmission cost model makes hard mute affordable in a way per-utterance muting was not.

Connection hygiene

  • Park permanently. No idle disconnect.
  • Prefer session resume over rejoin — resume emits no voice state change, no chime.
  • selfDeaf on send-only squad nets. Never selfMute — every listening bot must be able to play cues.
  • Transient undeafening for replies. A squad bot lifts selfDeaf via connection.rejoin({ selfDeaf: false }) for the duration of an open reply and restores it on close. Rejoin re-sends the voice state without changing channel, so it costs one gateway message and the latency hides inside the Dc cue window. Verify on the spike that rejoin produces no client-side join chime — it should not, since the channel is unchanged, but chimes are a stated product constraint (§4).
  • Re-deafening must be crash-safe: the boot sweep re-deafens every send-only net (§11).

07 Mirror & acks

Embed posted to source net chat and each target net chat at net open, so receivers can acknowledge while still listening. Transcript is edited in at close, when the async body transcription returns (§10). Target copies carry Acknowledge; press adds a reaction to the source copy.

A non-lead pressing Reply gets an ephemeral naming their lead. An unled net shows no lead assigned on the embed, so the commander can see why no answer is coming rather than waiting on one.

Ack reaction = regional-indicator emoji of the acking net's callsign (🇦 Alfa, 🇧 Bravo). Broadcast to 8 squads accumulates a letter row on the source message; missing letters are the outstanding nets. Reactions are display state; acks is the record.

08 Session lifecycle

/star-bridge

Ephemeral, button-driven. Q1 structure. Q2 net count, one button per available count up to free-slot ceiling; when exhausted, name the holding session and stop (no queue). On confirm: reveal channels, fleet joins, move invoker into command/first ops net, record as lead.

Ephemeral cannot host the control panel

Interaction tokens expire at 15 min; components become unupdatable. Sessions run hours. Panel is DM'd to the lead as a normal message, re-sent on transfer. DM rejected by privacy settings → fall back to a message in the Star Bridge text channel with handler-side lead check, ephemeral rejection for others.

Panel: End session · Pass lead (select menu of members on command net) · Mute others on/off · live status (nets, relay count, lead).

Squad leads

The fleet commander assigns one lead per squad or ops net, from the control panel: Promote squad lead → select the net → select the member.

  • No separate confirm step. Two deliberate selections already gate it, and it is reversible by promoting again. The real risk is not a mis-click but audio landing mid-transmission, and the queue rule in §5 handles that better than an extra click during an operation.
  • The member menu is populated from the target channel's voice states. Discord's native user select cannot be filtered to a channel's occupants, so this is a string select — 25-option cap, paginate above that.
  • Empty net → ephemeral “no one is on Charlie”, not an empty menu.
  • On commit: upsert squad_leads (one row per net, so promoting implicitly demotes the previous lead), queue the announcement into that net, post the text line, refresh the panel.
What a squad lead isv1

An unled net is acknowledge-only. No reply affordance appears until a lead is assigned — silent and predictable, and promotion is one dialog away. The commander's panel flags unled nets so this is never a mid-operation surprise.

Vacated silently when the lead leaves the net — no announcement, since an unprompted promotion cue mid-operation is noise. The panel shows the net as unled and the commander re-promotes. All leads are cleared at session end.

Teardown

5 min timer from last member leaving command/first ops net; rejoin cancels. On expiry: move remaining members in session channels to guild AFK channel, fleet leaves, overwrites re-denied, session closed.

  • No AFK channel → configured fallback channel → disconnect. Never leave a member in a hidden channel.
  • teardown_at persisted; boot sweep closes anything expired. Deploy mid-session must not orphan state.
  • Lead leaves without transfer → promote longest-present member on command net, DM them.

Announcement voice

Piper for both languages (da_DK-talesyntese-medium, any en_* voice), rendered once per (locale, spoken name) and cached in memory. The announcement string is a locale template — {name} er nu holdfører / {name} is now squad lead — resolved in the session locale, not the listener's, because a channel carries one audio stream (§5).

Locale pack = intent → accepted spoken forms, several per intent, extended via alias_variants. Many Danish units use English procedure words by convention — ship both, select per guild. Danish set above is a proposal, not a finding; check with the operators who will say them under load.

16 Build order

  1. Receive spike. One bot, @discordjs/voice@^0.19.2, decrypted per-SSRC PCM off the real guild under DAVE. ~50 lines. Gates everything.
  2. Fleet manager. N tokens parked, resume-preferring reconnect, fleet status. SQLite + boot sweep.
  3. Blind relay. Hard-coded source/target, raw copy, stream held open with silence frames. Measure latency, confirm no runtime chimes and no first-word clipping.
  4. Cue engine. Assets pre-encoded to Opus and cached, duration validation, playback into source and target simultaneously. Testable with a hard-coded call-up.
  5. Pool + sessions. Overwrite provisioning, wizard, lead, teardown, AFK move.
  6. Call-up protocol. VAD, STT driver, grammar parse, callsign matcher, SSRC suppression, per-net state machine, locks, timers.
  7. Mirror + acks. Embeds, buttons, callsign reactions, acks.
  8. Leads + reply path. Promotion picker, announcements, transient undeafening, reverse relay, text replies.
  9. Danish. Locale packs, hotword bias, corpus, variant learning.
  10. Admin. Licensing, install links, allowlist enforcement, stats.
  11. Prod. Compose overlay, GPU, backups, drain-before-deploy.

All 14 questions resolved 20 Aug 2026. The v1 answers below are the source of truth; the affected sections will be rewritten in the next artifact revision to fold these in.

#Questionv1 answerBlocks
1alert vs broadcast — resolvedalert: Horn cue, preempts a held net. broadcast: Attention cue, skips held nets. Danish Attention localises to Giv Agt.—
2Callsign namespace flat per guild or per session — resolvedFlat per guild. v1 uses named callsigns rather than raw NATO letters.
• Command mode nets: Command, Alpha, Bravo, Charlie.
• Joint operations nets: Head Ops, Alpha Ops, Bravo Ops, Charlie Ops.		§3
3Who may trigger a relay — resolvedSession owner appoints a lead in every net. The lead in the owner's command net is the XO and holds the same speaking rights as the owner — both can hail, command, alert, broadcast. Squad leads may only reply to the command net (see #13).§5, §8
4Fleet size at launch — resolvedv1 ships 4 applications: one main (controller, also the command-net voice presence) plus Alpha, Bravo, Charlie. Fleet expansion is future work.§2
5da or en procedure words on your nets — resolvedPer-guild locale, one setting. Both en and da packs shipped. Per-guild cue override is future work.§10
6Self-hosted or streaming cloud STT — resolvedLocal TTS and STT. No cloud dependency in v1.§10
7Do squad nets answer by voice? — resolvedYes, but only the lead, and only button-gated. No detection on squad nets, so recognition cost does not scale with total nets.—
8Dc cue length — resolved1200 ms; tune against a real net once real cues are recorded.§5
9Cue voices: shipped TTS (Piper da/en) or your own recordings — resolvedShip TTS defaults. Operators drop replacement files at the same paths to override. Per-guild cue upload UI is future work.§5
10Out close cue — wanted, or silence? — resolvedTwo-part close: caller may say "Over" (Danish "Slut") as a spoken terminator, and net close plays a short squelch / scratch SFX (locale-neutral) in both source and target. Replaces the silent close of earlier drafts. Per-guild toggle retained.§5
11What powers should a squad lead carry? — resolvedThe reply channel: only the lead answers the commander. Everyone else gets Acknowledge, and the lead's ack is the authoritative one.—
12Is the member's name in the audio worth adding a TTS runtime? — resolvedYes, in the guild's locale. TTS renders member display names for lead-assigned announcements. Per-user recorded callsign is future work.§5, §10
13Should a lead's reply be relayed to the other squads, or only to the commander? — resolvedCommander only — squad nets stay isolated from each other. XO (the command-net lead) carries the same rights as the owner.§5
14May the commander revoke a reply mid-transmission? — resolvedTerminator behaviour ends the reply naturally. "Over" followed by a short pause closes the net; a longer silence (silence_close_ms) closes it without a terminator. max_hold_ms still caps runaway holds. Explicit cut-off is future work.§5, §8

#7 was the architectural fork and it resolved cheaply. Squad nets do answer by voice, but because the reply is button-gated rather than spoken, squad bots only ever receive — they never detect. STT stays proportional to command nets. The cost the question warned about does not materialise.
