01 Scope

Star Comms is a Discord bot fleet that opens brief, cue-signalled voice-to-voice bridges between separate voice channels in one guild. It is aimed at slow-tempo cooperative play — industrial gameplay, exploration, coordination between wings, station comms — where the participants sit in their own channels and occasionally need to talk to another channel's owner without either party leaving their own voice channel.

A channel owner presses a button, the bot picks a target from a directory of hailable channels, and audio flows both ways for as long as anyone talks. Every action is user-initiated through slash commands or button clicks.

In

  • Per-user voice channels created via a server-conventional join-to-create lobby.
  • Owner-driven control panel with buttons for rename, lock, member limit, kick, ownership transfer, hail opt-in, and hail.
  • Per-guild callsign registry: members pre-register a ship name, then opt their currently-owned channel into the hail directory.
  • Bidirectional voice bridge between the owner of the hailing channel and the owner of each hailed channel. Owner audio only; crew audio stays local to their own channel.
  • Ready / Attention / Ring / Busy / End cues on channel transitions.
  • Per-channel end button and a 10 s all-quiet auto-close.
  • SQLite on host-mounted volume. Compose for dev and prod.
  • Interface strings in en + da. No voice model dependency.

Out

  • Audio recording, archival, or transcript. No audio touches disk.
  • Star Comms does not manage the guild's static voice layout — only vessels created via join-to-create.
  • Cross-guild bridges within one hail.
Audit trail

Every hail is written to a text-only audit: who called whom, when, for how long, and which channels participated. No audio content.

02 Fleet

One voice connection per bot user per guild — hard Discord limit, open and unanswered since Oct 2022. Star Comms is N Discord applications, N tokens, one process.

Since a hail requires one bot in each participating channel, N caps how many channels can be simultaneously involved in hails at the same time in one guild:

FleetConcurrent channels-in-hailExample configurations
22One 2-way hail
33One 3-way, or a 2-way + a leftover
44Two 2-way hails, or one 4-way

v1 ships with 4 applications: one controller which registers slash commands and holds channel-management permissions, and three relays allocated to voice channels as hails require. The controller never joins voice in v1 (upgrade path is trivial: make it pool-eligible when a 4th concurrent channel is needed).

Provisioning is manual

No Discord API creates applications. Each app is hand-registered in the developer portal with the SERVER MEMBERS privileged intent enabled. Tokens are shown once.

Bots are permanent Discord identities but transient voice-channel occupants: they connect their gateway on process start, log in, and stay parked outside voice until allocated to a hail leg. On hail close they leave voice.

Join chime is acceptable

Discord's client plays a join chime when a bot enters a voice channel. In slow-tempo comms this is fine — hails are minutes apart, not seconds — and the chime is a useful audible cue that a hail is opening even before the Ring/Attention cue plays.

03 Vessels

Star Comms does not create a category and does not pre-create any voice channels. It relies on the guild's existing join-to-create convention — a well-known voice channel that any member can join to be automatically moved into a fresh channel of their own. Many game-community servers already have this configured; Star Comms plugs into the operator's existing one.

Setup

/star-comms watch-channel presents the invoker with a select menu of the guild's voice channels. The invoker picks the join-to-create trigger, and the id is stored in guilds.join_to_create_channel_id. No channels are created by this command. Re-running /star-comms watch-channel replaces the stored id.

/star-comms set-language presents a select menu of the supported locales (labels written in the language itself) and stores the choice in guilds.locale. Language is a guild setting: Discord renders a bot's buttons and posts identically for every member, so there is no per-user variant. The choice governs every reply, every button label, the slash-command descriptions (re-registered for that guild on change) and the voice cues. Cue audio is per locale (cue_sets.<set>.<locale>); a locale whose audio is not installed is still selectable — text switches at once and the default locale's cues play until the files exist. Every live control panel in the guild is re-rendered in the new language immediately (via the vessel's stored panel_message_id); active hail messages are not touched. The same in-place re-render runs on /star-comms register and unregister for the panels of vessels the invoker owns, so Allow hails becomes enabled (or disabled, with the vessel dropped from the hail directory) without waiting for a click — and once at boot for every live panel, so a deploy that changes the panel's layout or button set updates panels posted by the previous version immediately.

Vessel channel creation

Star Comms listens for voiceStateUpdate. When a member joins the guild's configured join-to-create channel:

  1. The controller creates a new voice channel. Default name is 🔊 [display name]. Parent is the join-to-create channel's parent category (so vessels appear next to the trigger, in whatever category the operator's convention channel lives in — Star Comms does not manage the category itself).
  2. The controller MOVE_MEMBERS' the member into the new channel.
  3. A row is inserted into vessels with the channel id, owner user id, guild id, and creation time.
  4. The bot posts the control panel message in the vessel channel's built-in voice-text chat (see §4).

Vessels are automatically deleted when they go empty (no members present) — standard join-to-create behaviour. When a vessel is deleted, any active hail leg it belongs to closes for that leg (§6).

Owner leaves

When the vessel's current owner leaves the vessel channel:

  • Their hail_registry row (if any) is dropped — the channel is no longer discoverable in the hail directory.
  • The controller attempts to rename the channel 🛰️ … → 🔊 …. If Discord's rename PATCH rate limit refuses, the visual stays; the channel is no longer registered in either case.
  • Any hail leg the vessel was part of is closed as if the owner had pressed [End hail] (§6).
  • Remaining members in the vessel can continue talking as they would in any Discord voice channel. When the channel empties, standard join-to-create cleanup deletes it.

Ownership transfer

Ownership moves in two ways, both through the same rename-gated routine:

  • Automatic. When the owner leaves and other humans remain, a 30 s grace window starts (a rejoin cancels it). After it, the longest-present remaining member becomes owner.
  • Manual. The owner presses Transfer on the control panel (§4), picks one of the humans currently in the channel, and ownership moves immediately. Refused while the vessel is in a hail — a hail leg is bound to the owner's voice.

The routine renames the channel to 🔊 [new owner display name] first and does nothing else unless that succeeds: a vessel carrying the old owner's name or callsign after a transfer is confusing, and the rename is the one step Discord can refuse (~2 renames per 10 min per channel). On refusal the database is untouched. The manual path reports it to the owner ("try again in ~10 minutes"); the automatic path retries every 60 s, up to 15 times, while the owner is still absent and the channel still populated. On success the vessels.owner_user_id row is updated, the hail_registry row is dropped (the callsign belonged to the old owner, so hails are off), the control panel is re-rendered in place, and a notice is posted in the channel.

For this gate to work the controller's REST layer is configured to reject a rate-limited PATCH /channels/:id (rejectOnRateLimit) rather than the library default of silently queueing it for up to 10 minutes. Only that route is affected.

04 Control panel

Posted automatically in the vessel's voice-text chat immediately after the owner is moved in. Content is a mention of the owner plus a two-row action bar of buttons:

ButtonEffect
RenameOpens a modal with a text input. On submit, PATCH the channel name.
Lock / UnlockToggle. Locked adds a permission overwrite denying CONNECT to @everyone. Existing members are unaffected.
LimitOpens a modal with a numeric input. Sets user_limit on the channel. 0 disables the limit.
KickOpens a member-select from the channel's current members. Disconnects the selected member from voice.
TransferOpens a member-select of the humans currently in the channel (excluding the owner). Hands ownership to the pick via the rename-gated routine in §3: refused if the rename is rate-limited or the vessel is in a hail; otherwise renames, disables hails, re-renders the panel and posts a notice.
Allow hails / Disable hailsRequires the owner to be pre-registered (§5). Allow adds a row to hail_registry and renames the channel 🔊 … → 🛰️ [callsign]. Disable removes the registry row and renames back to 🔊 [display name]. Both PATCHes count against Discord's ~2-per-10-min rename bucket, so Allow → Disable → Rename in quick succession will 429 on Rename with a ~10 min wait.
HailRequires the owner's own channel to have hails enabled. Opens a channel-select populated from hail_registry (excluding self). See §6.

Every button handler validates that the interaction's user is the vessel's current owner (join row in vessels). Non-owner clicks respond with an ephemeral "Only the channel owner can use these controls."

Rate-limited actions

Channel name / topic PATCH is capped at ~2 per 10 min per channel. On a rate-limited response Star Comms replies to the button click ephemerally with "Discord's rename limit for this channel is reached. Try again in ~10 minutes." — no queueing, no retry loop.

The control panel message is not ephemeral (Discord ephemerals require an existing interaction to reply to, and vessel creation is triggered by voiceStateUpdate, not by a slash command). It remains in the voice-text chat's history for future channel members, which is acceptable — the buttons enforce owner-only access, and non-owners see the channel status but cannot change it.

05 Callsigns

Callsigns are guild-scoped, unique per guild, one per member. They are the ship name a member wants displayed on their vessel and shown in other members' hail directories.

Slash commands

  • /star-comms register <callsign> — registers or replaces the invoker's callsign in this guild. Rejected if the callsign is already registered by someone else in this guild.
  • /star-comms unregister — removes the invoker's callsign. If the invoker currently owns a hail-enabled vessel, the vessel's hail_registry row is dropped as a side effect.
  • /star-comms callsign — reports the invoker's current callsign, or "not registered" plus a one-line prompt to /star-comms register.

Callsigns are stored in the callsigns table (§10). Renaming a callsign does not auto-rename any existing vessel channel — respecting the ~2 PATCH per 10 min rename bucket. The new callsign will apply the next time the owner clicks Allow hails.

Why registration is separate from vessel creation

Two reasons. First, it decouples identity from a specific channel — a member can register once and go through many vessels over time without re-typing. Second, the vessel-creation flow is triggered by joining a voice channel, which is a bad moment for a modal (the member has already committed to the join, no room to prompt for text input). Registering ahead of time keeps the vessel-creation path silent and instantaneous.

06 Hail

A hail is an audio bridge between two or more vessel channels, opened on demand by a channel owner. Owner audio only crosses the bridge; other members' audio stays local to their own channel and is inaudible to the far end.

Opening a hail

owner clicks [Hail]→ select-menu of hail_registry→ allocate free relay bots→ bots join each participating channel→ Ring in locked, wait for accept→ Ready + Attention synced→ bidirectional relay

Steps:

  1. The owner of a hail-enabled vessel clicks Hail on their control panel.
  2. The bot presents a multi-select menu of currently-registered hail channels, excluding the owner's own vessel. Selecting no targets cancels.
  3. The allocator picks a free relay bot for each participating channel — including the caller's own. If not enough bots are free the caller receives an ephemeral "All relays are busy — try again in a moment" and the hail is cancelled.
  4. Each allocated bot joins its assigned channel. Unlocked targets are considered accepted immediately. Locked targets enter the ring phase per §6.2.
  5. Once every selected target has resolved (accepted or declined):
    • If at least one target accepted: all bots on the caller's side and every accepted target's side play Ready and Attention respectively on the same instant (§7). Cue duration Dc masks the join latency and ensures the message body starts after every listener has already heard the alert.
    • If every target declined or timed out: the caller's bot plays Busy; every allocated bot leaves; the hail ends without opening.
  6. The bidirectional relay opens between the caller and the accepted targets. Each participating channel gets an End hail button posted in its voice-text chat.

Acceptance

Target stateBehaviour
Hail-enabled, unlockedAuto-accept. No Ring. Attention plays in that channel at the synchronised open (step 5).
Hail-enabled, lockedBot joins the channel and plays Ring repeated at ~4 s intervals for up to 20 s, alongside an Accept / Decline button pair posted in the target's voice-text chat. Accept marks the target accepted. Decline or 20 s of inactivity marks it refused; the bot leaves the target channel silently.
Not hail-enabledNot listed in the caller's select menu in the first place — cannot be targeted.

Closing

Two independent close paths:

  • Per-channel end button. Each participating channel's voice-text chat carries an End hail button posted at hail open. Any member of that channel who is either the vessel's owner or holds MOVE_MEMBERS may press it. Pressing plays End in that channel, its bot leaves voice, and the channel drops from the hail. If only one channel remains after a drop, the hail auto-closes on that channel too.
  • 10 s all-quiet timer. Each relay bot tracks whether its channel's owner is currently speaking (via receiver.speaking events, owner user id only). A hail-wide clock records the timestamp of the last owner speech across all channels. When Date.now() − lastSpeech > 10_000, the hail closes on every side: End cue everywhere, all bots leave.
Why 10 s

Long enough that a natural pause between exchanges — "OK, moving in… (pause) … in position" — does not cut the hail. Short enough that a completed conversation ends promptly. Configurable per guild via guilds.hail_silence_close_ms.

State recording

Every hail open, accept, decline, per-channel end, and auto-close is written to the hail_events audit trail (§10). Peak concurrent bots and total duration are recorded on the active_hails row at close time. This is the "who called whom, when, for how long" surface — sufficient for admin review without any audio content.

07 Cues

Cues are short pre-encoded Opus assets played by a bot into its channel at defined moments in the hail lifecycle. Pre-encoded to Opus frames and cached in memory at startup — no ffmpeg spawn per cue, constant playback latency.

CuePlays inTrigger
Readycaller's channelevery selected target has resolved and at least one accepted; the hail opens
Attentioneach accepted target channelsame instant as Ready
Ringlocked target channelhail requested against a locked target; repeats every 4 s until Accept, Decline, or 20 s of no click
Busycaller's channelevery selected target refused (declined or timed out), or the allocator had no free bots
Endthe channel closinga per-channel End hail button, or the hail-wide 10 s all-quiet auto-close

Cue sets are per guild (shipped defaults or operator-supplied WAVs). Ready and Attention must be equal length Dc — startup validates and fails loudly on mismatch — because they play in different channels on the same instant, and their common end defines when the caller can start speaking. Ring, Busy and End play alone and are not subject to the strict-equal invariant, but the validator still checks their duration against Dc ± 200 ms so operator-supplied packs stay coherent.

Timers

SettingDefaultEffect
cue_duration_ms (Dc)1200All equal-length cue assets normalised/padded to this length
ring_interval_ms4000Gap between repeated Ring plays in locked channels
ring_max_ms20000Total ringing budget for a locked-channel target; auto-decline after
hail_silence_close_ms10000Hail closes if no participating owner has spoken for this long
hail_max_hold_ms1800000Hard cap on a single hail (30 min). Safety net; typical hails end long before this.

08 Audio path

Each participating channel gets one relay bot. Each relay bot runs two audio directions simultaneously:

  • Send: subscribes to the channel's owner SSRC via receiver.subscribe(ownerUserId). Forwards the raw opus stream to every other participating bot's outbound player.
  • Receive: its outbound AudioPlayer plays whatever the other bots forward in. Bot transmits into the channel via a selfDeaf: false, selfMute: false voice connection.

Only the owner's SSRC is subscribed on the send side. Other members in the channel talk locally — Discord's client mixes their audio for humans in the channel — but their audio is not picked up by the bot and not forwarded across the hail. This is the "captain-to-captain radio" semantic.

Multi-way hails and simultaneous speakers

A bot's AudioPlayer can transmit only one opus stream at a time. When two remote owners speak simultaneously into a hail with three or more participating channels, the local bot picks up two inbound streams but can transmit only one — last-speaker-wins in v1. If Firefly and Serenity both talk into a 3-way hail with Explorer, whichever's opus arrived at Explorer's bot most recently is what Explorer hears; the other stream is stepped on.

Mixing is future work

Proper N-way mixing requires decoding each inbound stream to PCM, summing, re-encoding to opus per outbound target. ~10 ms CPU per active speaker per receiving side, no crypto involvement. Ships in a follow-up if last-speaker-wins turns out to bite in real use.

Hard audio constraints

  • § Fleet SSRC suppression. Every bot filters its own receiver.speaking.on('start') events against the fleet's user id set. Without this, cues played by another relay bot in the same channel — impossible in v1 because at most one bot ever sits in a channel, but the guard remains — would loop through the hail. This is a permanent invariant, not an implementation detail.
  • § No audio to disk. Opus frames are relayed in memory. There is no recording, no transcription, no archival path.
  • § selfMute is never set. Every relay bot must be able to play cues into its channel.
  • § Voice-adapter routing. Every joinVoiceChannel uses the joining bot's own Guild.voiceAdapterCreator — never the interaction guild's, which is the controller's. Recorded as a hard constraint in CLAUDE.md.
  • § Per-bot group on joinVoiceChannel. Set group: userId or the connection will collide with another bot in the same guild.
  • § maxMissedFrames: Infinity on outbound players fed from receiver streams. Default 5 kills the resource on inter-word pauses.
  • § Tolerate DAVE decrypt errors. AudioReceiveStream and its consuming AudioPlayer both need 'error' listeners that swallow DecryptionFailed(UnencryptedWhenPassthroughDisabled) and continue.

Boot sweep reads three tables before the fleet connects to Discord: active_hails (any row without closed_at is force-closed with reason drain), vessels (any row whose channel_id no longer exists on Discord is marked deleted_at), and hail_registry (any row whose channel no longer exists is dropped). A crash mid-hail leaves stale state; this repairs it before the fleet touches voice.

Backup: nightly sqlite3 .backup to the mount, 7-day rotation.

12 Deployment

Single process runs controller + all relays; no relay crosses a process boundary. Split only if we ever exceed one machine's UDP send capacity — not a v1 concern.

docker-compose.yml            # bot service, volumes, healthcheck
docker-compose.override.yml   # dev: source-mounted, watch mode
docker-compose.prod.yml       # prod: pinned image, no bind mount
Dockerfile                    # multi-stage, Debian slim
                              # native: better-sqlite3, @snazzah/davey, @discordjs/opus

/star-comms drain before deploy. Restart mid-hail is survivable — bots reconnect and the hail is reopened only if participants press Hail again; there is no automatic resume of an in-flight hail across a restart.

Debian, never Alpine

@snazzah/davey (DAVE end-to-end encryption), @discordjs/opus, and better-sqlite3 are native modules; musl breaks them. Enforced in the Dockerfile FROM node:22-bookworm-slim.

15 Build order

  1. Clean legacy code. Prune modules that do not serve this design (src/detection/, src/session/model.ts, src/session/router.ts, the pre-existing session-oriented slash surface). Rename every identifier to the star-comms namespace — slash commands, project name, invite text; the internal SB_TOKEN_* env var names stay as-is. Retain the fleet manager, cue engine, the DAVE-receive spike, and the audio-relay primitive (generalised into runHailLeg in step 6).
  2. Vessels. voiceStateUpdate listener on the controller. On join-to-create, create channel + move owner + insert vessels row + post control panel. Auto-delete on empty.
  3. Callsign registry. /star-comms register, unregister, callsign. DB uniqueness. No rename side effect.
  4. Control panel buttons. Rename, Lock/Unlock, Limit, Kick. Owner-only handler check. Rate-limit-tolerant PATCH.
  5. Hail registry. Allow-hails / Disable-hails buttons. Rename to 🛰️ callsign on Allow.
  6. Hail: 2-way. Hail button, target multi-select, allocator, cue pair, bidirectional relay between two channels. Per-channel End button. 10 s all-quiet close.
  7. Ring + accept/decline. Locked-channel acceptance UX with the 20 s ring window.
  8. Hail: N-way. Extend the relay to three-plus channels with last-speaker-wins on the outbound side. Documented crosstalk risk.
  9. Admin polish. /star-comms status, drain, hail-registry. Boot sweep of stale state.
  10. Prod. Pinned image, backup cron, drain-before-deploy.

Each step is a git commit with tests where testable and a manual verification bar where not. The DAVE-receive spike (npm run spike) remains the fastest smoke test that inbound audio still decrypts on the current stack.
